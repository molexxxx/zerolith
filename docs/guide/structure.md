# Application structure

One layout serves every path: an application that runs from an import map, one that Vite bundles, and one that a server renders all keep the same files in the same places, so a reader, a tool, or an agent that knows one zerolith project knows them all. `zerolith new` writes this layout; the sections below say what each part is for.

```
my-app/
    index.html              the page: an import map, or a module script that Vite serves
    AGENTS.md               the map and the rules, for coding agents and new contributors
    .agents/skills/         the zerolith skill, for Codex, Cursor, GitHub Copilot, and most agents
    .claude/skills/         the same skill, for Claude Code
    package.json            scripts: dev, build, check, typecheck, lint, test
    openapi.json            the server's contract, when it publishes one
    messages/               message catalogs, one <locale>.json per language
    src/
        main.ts             mounts the application: messages, router.ready, render
        routes.ts           the route table, one entry per page
        router.ts           createRouter over the table, imported by components for href
        store.ts            signals, resources, and the operations that change them
        schema.ts           Standard Schemas shared with the server
        locale.ts           the locale signal and the message loaders
        api.ts              generated by zerolith-client from openapi.json
        messages/           generated by zerolith-i18n from messages/
        components/         one file per screen or widget, functions that return views
        styles.css          tokens, resets, and global rules; component styles are css literals
    test/                   browser tests with @zerolith/test
```

A JavaScript project has the same layout with `.js` files and JSDoc types; `npm run typecheck` checks both.

## What each file owns

- `main.ts` does the three things that happen once: wait for what the first paint needs (messages, `router.ready`), render the layout around `router.outlet()`, and start development-only tools such as the inspector. Nothing else is global.
- `routes.ts` is the single list of pages. Each route names its view function, its loader, and its head metadata; the router infers the parameters from the path string, so a wrong `href` fails `tsc`.
- `router.ts` creates the router so that components can import it for `href` and `navigate` without a cycle through the route table.
- `store.ts` is where signals and resources live when more than one component reads them. State that only one component needs stays inside that component.
- `components/` holds functions that return views, one screen or widget per file, each with its `css` literal next to the markup it styles. Their names start with a capital letter: the hot replacement in the Vite plugin and the JSX lowering both rely on it.
- `api.ts` and `src/messages/` are generated. They are checked in so the project builds without running the generators, and regenerated with `zerolith-client` and `zerolith-i18n` after their inputs change. `AGENTS.md` says so, so nobody edits them by hand.
- `schema.ts` holds the Standard Schemas a form validates with, so the server can import the same module and run the same checks.

## Conventions the tooling relies on

- A component is a capitalized function that takes one props object and returns a view. Children are the `children` prop. In a `.tsx` or `.jsx` file the view can be spelled as JSX; it lowers to the same `html` call.
- State that must survive an edit during development is a named signal: `signal(0, { name: "count" })`. Both `zerolith dev` and the Vite plugin restore named signals; anonymous ones start over.
- Routes that are not needed on first paint use `lazy()`, and each locale's messages are their own module, so the bundler splits them without configuration.
- Relative imports carry the file extension, so the same source runs unbundled.
- `.get()` is called inside `computed`, `effect`, `resource.params`, and event handlers; a template binds the signal itself.

## The AGENTS.md

An agent reads one file before touching a project. The scaffold writes this one for `zerolith new my-app`, a TypeScript project on the command line, and the point of its shape is that it fits in context next to the task:

```markdown AGENTS.md
# my-app: guide for coding agents

A zerolith application. The project develops and builds on the zerolith command line; packages load from `node_modules` with no import map, and there is no Vite config. This file holds what is specific to this project. zerolith's own rules and patterns are in the zerolith skill in `.agents/skills/zerolith/`, also at `.claude/skills/zerolith/` for Claude Code; `npx zerolith skill` brings it to the installed version after an upgrade. The guides at https://molexxxx.github.io/zerolith/guide/ cover each concept in full.

## Commands

- `npm run dev` serves the app with live reload; `npm run build` writes `dist/`; `npm run preview` serves `dist/`.
- `npm run check` is the gate: typecheck, lint, browser tests, and the build.
- With `@zerolith/client` installed, `npx zerolith-client openapi.json --out src/api.ts` regenerates the typed client from the API contract; with `@zerolith/i18n` installed, `npx zerolith-i18n messages --out src/messages` regenerates the message modules.

## Rules

- Bind the signal, not its value: a live binding takes `count`, never `count.get()`, which freezes. Call `.get()` only inside `computed`, `effect`, `resource.params`, and event handlers.
- Components are capitalized functions returning `html` templates, one per file under `src/components/`, with their `css` literal next to the markup.
- State that must survive an edit is a named signal: `signal(0, { name: "count" })`.
- `src/api.ts` and `src/messages/` are generated when they exist; change their inputs and regenerate, never edit them.
- A new page is a route in `src/routes.ts` and a component; shared state goes in `src/store.ts`, created with the first piece of it.
- Files served as they are, such as data, icons, and `robots.txt`, go in `public/`.
- Only `.env` variables named `PUBLIC_*` reach the browser, as `import.meta.env.PUBLIC_*`.

## Where things go

| Change | Location |
| --- | --- |
| A page | `src/routes.ts` and `src/components/<page>.ts` |
| Shared state or a request | `src/store.ts` |
| A message, once the project uses `@zerolith/i18n` | `messages/<locale>.json`, then regenerate |
| A style token | `src/styles.css`; component styles stay in the component |
| A static file | `public/` |
```

The framework's rules live in the zerolith skill rather than in this file, so the file stays about the project. The [coding agents guide](agents.md) covers what an agent reads and when.

## Scaffolding

The command line comes from npm as `@zerolith/cli`, so `npx @zerolith/cli@alpha new my-app` needs nothing installed first; see [Command line](command-line.md).

```
zerolith new my-app                        asks, with TSX and the command line as the defaults
zerolith new my-app --yes                  takes every default
zerolith new my-app --template js          JavaScript with html templates and JSDoc types
zerolith new my-app --vite                 develops and builds on Vite with @zerolith/vite
zerolith new my-app --buildless            deploys the modules behind an import map instead of a bundle
zerolith new my-app --example fullstack    the fullstack example: an app under /app/ with its own Node backend
```

By default the command writes the layout with three working pages, a browser test, the scripts, a README on developing and deploying, the `AGENTS.md`, and the zerolith skill, pinning the tool versions this repository tests with, and installs the dependencies. `cd my-app && npm run dev` starts it.
