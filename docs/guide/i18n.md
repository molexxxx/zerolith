# Internationalization

Every engine already formats numbers, dates, lists, and plurals for every locale through `Intl`, so `@zerolith/i18n` ships no locale data and no message runtime. It decides which locale, keeps it as a signal, and compiles message catalogs ahead of time into plain functions, one module per locale, so a locale is one chunk and the hot path is a string concatenation.

## The locale

`createLocale` negotiates what was requested, an `Accept-Language` header on the server or `navigator.languages` in the browser, against the locales the application supports, the way RFC 4647 lookup does: an exact match first, then the request with subtags dropped, then a more specific supported locale of the same language, then the fallback. The result is a signal, with the writing direction derived from it.

@include packages/i18n/test/examples/i18n.example.test.ts#locale

`applyLocale(locale)` keeps `<html lang dir>` in step with the signal. `formatters` wraps `Intl.NumberFormat`, `DateTimeFormat`, `RelativeTimeFormat`, `ListFormat`, and `PluralRules`, cached per locale and options; each call reads the locale signal, so a `computed` value or a template binding that formats re-renders when the locale changes and nothing else does.

In a routed application the locale is a route segment: declare paths such as `/:locale/notes/:id`, pass `params.locale` to `set`, and build links with `href` as usual. Negotiating on the server and redirecting a bare `/` to `/de/` keeps the URL the single source of truth.

## Messages

Catalogs are JSON files, one per locale, whose values are MessageFormat 2, the Unicode standard that succeeds ICU MessageFormat: plain text with placeholders, functions such as `:number` and `:datetime` with their options, and `.match` for plural and other selection. This is `messages/en.json`:

@include packages/i18n/test/fixtures/messages/en.json

Compile the folder into modules:

```sh
npx zerolith-i18n messages --out src/messages
```

The command compiles every `<locale>.json` in the folder into `<locale>.ts` (or `.js` with `--js`, with JSDoc types, for buildless projects) and an `index.ts` whose `loaders` import one locale at a time. Each message becomes a function named from its key, with an `args` object typed from the placeholders: a variable formatted with `:number`, `:integer`, `:percent`, `:currency`, or `:offset` is a `number`, one formatted with `:date`, `:time`, or `:datetime` is a `Date | number`, and anything else is a string or a number. A key that some locales lack is reported, and `--strict` makes it fail the build.

The application imports the functions it needs:

@include packages/i18n/test/examples/i18n.example.test.ts#use

Selection follows the specification: an exact numeric key beats a plural category, which beats `*`, and with several selectors the keys are compared left to right. The compiler covers the subset catalogs use, which is text and placeholders, quoted and unquoted literals, `.input` and `.local` declarations, `.match` with numeric and string selectors, and the default functions `:string`, `:number`, `:integer`, `:percent`, `:currency`, `:offset`, `:date`, `:time`, and `:datetime`; markup such as `{#b}` is accepted and formats to nothing. Anything outside that subset fails at compile time with the message's key, never at run time with a fallback string.

## Loading one locale

```ts
import { loaders } from "./messages/index.ts";

const messages = await loaders[locale.locale.get()]?.();
```

Each locale module is independent, so a bundler splits it into its own chunk and an import map serves it as its own file; with `@zerolith/vite`, a build that imports a locale module statically fails with [`lazy_module_not_split`](/e/lazy_module_not_split/), since that would pull it into the importing chunk. Switching locales loads the next module and re-renders what reads it; nothing about the first locale stays in memory except what the engine caches for `Intl`.
